# Next to-dos
- [ ] Enable two-way sync on Markdown Viewer to PDF Viewer (keep the PDF viewer in sync with the Markdown viewer on page changes). That way, as the current sentence progresses across page boundaries (during listening or from seeking), the PDF in view matches the Markdown being viewed.
- [ ] When editing the Markdown, keep the scroll position the same as it was in the rendered view, making the transition smooth between rendered text and the editing experience. Otherwise, when users click the edit icon, they need to scroll to find the position where they were just viewing. On a 100-page PDF file, it can be tricky for users to find where they were without synchronized scroll positions between the editing and rendered views.
- [ ] On the estimated remaining time on the playback bar (bottom-right corner), display hours:minutes:seconds rather than just minutes:seconds, so that the time looks like `-6:22:45` instead of `-382:45`.
- [ ] Enable voice clone management: rename and/or delete
- [ ] Load PDF viewer and postprocessing options prior to OCR, with an "extract text" button to kick off OCR
    - [ ] Enable editing page offset (for first page); useful when scanned pages are not the start of the book (e.g., chapter by chapter scan)
    - [ ] Enable editing per-page numbers (useful when scanned pages skip physical pages; like when a page is only an illustration, so there would be no text to extract). This could be done, for example, by showing an editable page number on the PDF viewer that will be used for the "Page #." blocks added in postprocessing.
- [ ] Refine estimates of playback ETA by tracking total words (or maybe characters for simplicity?) processed and the total time for those words; stored in LocalCache, by voice and TTS engine (where the total time is always calculated based on a speech rate of 1.0). Then, the estimates will improve over time because they are being refined.
- [ ] Show voice clone name in the URL query parameter instead of the voice ID; avoid conflicts by appending "-voice-clone" or something like that if the cloned voice name conflicts with a built-in voice name; or show a warning explaining the conflict so the user can rename the voice.
- [ ] Add a dedicated show/hide button for the PDF viewer, rather than the "click the top-left logo" behavior. Instead, the top-left logo should land at an overview page showing the user where they can pick up again (e.g., select an item from a playlist to resume listening; or create a new playlist). A playlist is a group of items to be listened to in sequence with autoplay (the next item starts automatically after the current item completes).
- [ ] Support digital-native PDFs with text embedded in them and extractable via `pdfplumber` rather than OCR
- [ ] Migrate to a full playlist library: URL fetching and processing to Markdown; plain Markdown upload or copy-paste into a text area; PDF support for digital-native PDFs (use `pdfplumber` to extract text); ePub documents, and PDF URLs so the user doesn't need to download and then upload PDFs that are already available publicly online. Include a dedicated library management pane with item reordering and renaming and auto-play to the next item when the current one finishes. Each item card in the library will show the current progress through that item along with the estimated total listening time and remaining time. The item cards will also display their source (PDF upload, plain Markdown upload or copy-paste, article URL/domain for URL-fetched items, domain for URL-fetched PDFs).
    - [ ] I created a wire-frame mock-up in tldraw to clarify what the UI should look like: [wireframes](./docs/ui-design/)
    - [ ] The PDF viewer pane will become an optional pane that can be shown to compare with the OCR version of it (or simply the text-extraction version if a digital-native PDF was used)
- [ ] Full audio file generation. An asynchronous process on the backend server (doesn't block the UI or the server if already running TTS); perhaps a separate process or worker to manage it. Basically, the user selects "download full audio TTS" and the frontend kicks off a process on the backend to generate a full audio file. We can show progress if it is feasible, otherwise, just notify the front-end via a toast that the download is ready. The user can then download the file from the library item card in the library manager pane. The audio should probably be compressed automatically before being made ready for download, from WAV to mp3 or webm audio or some other compressed format to reduce the file size while preserving quality (we can probably do that with the `pyav` library). **One note here: the browser already saves generated audio during normal playback: after the server is shut down, a user can still play back previous sentences since the TTS outputs are cached by the browser. In that case, we could consider surfacing an option to download the already-listened-to audio, perhaps listing the sentence range (or section range) for which TTS audio is already available.
